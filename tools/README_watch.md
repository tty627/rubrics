# 监控面板使用说明

## 两个版本对比

### panel.py（主面板，修正归因错误）
- 686行代码，分清「我们的流量」和「端点整机负载」
- **修正三个旧版归因错误**：
  1. 端点 `/metrics` 是整机口径（含他人），明确标注，不与本流水线混淆
  2. 过期步骤检测：输出早于输入时标 `⚠ 产出早于输入`，不误报完成
  3. 数据口径交叉验证：声明的 seed vs. s01 实际行数，不一致时报警
- 进度条、速率趋势、在飞请求、模型归属（从 cache 文件读，唯一权威）
- 适合：日常监控、确认「到底在用哪个模型」

### watch.py（详尽模式，保留用于调试）
- 1000+ 行代码，8个信息区块
- 显示进程详情（pid、socket连接、环境变量）
- 显示在飞请求的完整 prompt/output
- 显示最近完成调用的详细内容
- 显示产出文件列表
- 适合：深度调试、排查问题

## panel.py 用法

### 基本用法
```bash
# 全屏实时刷新（推荐）
python3 tools/panel.py

# 快照模式（打印一次退出）
python3 tools/panel.py --once

# 展开所有步骤（包括未开始/已完成）
python3 tools/panel.py --all

# 自定义刷新间隔（默认2秒）
python3 tools/panel.py -n 5

# 不探测端点（纯本地）
python3 tools/panel.py --no-probe
```

## 四层信息结构

### 1. 状态栏
- **数据口径** - 声明的 seed vs. 实际处理的行数（交叉验证）
- **当前任务** - 正在运行的脚本 + 已跑时长
- **在飞请求** - 当前在路上的请求数

### 2. 进度表
- **活跃步骤** - 正在运行或最近有活动的步骤
  - 进度条：12字符，满格表示完成
  - 速率：次/分钟
  - 趋势：↑加速 →平稳 ↓减速
  - ETA：预计剩余时间
  - 模型：从 cache 文件读取的实际归属（不是环境变量推的）
- **过期步骤** - 产出缺失或早于输入的步骤（`⚠` 标记）
- **折叠信息** - 已完成和未开始步骤默认折叠（用 `--all` 展开）

### 3. 本流水线的调用（权威口径）
- **数据源** - `cache/<stage>/*.json` 里的 `model` 字段
- **Token 用量** - 输入/输出/思维链占比
- **在飞状态** - 每个模型当前在路上的请求数
- **未被调用** - 配了但一次没用过的模型（显式列出）
- **调用统计** - 最近成功率、平均耗时

### 4. 端点（整机口径，含他人）
- **明确标注** - 「整机口径，含其他租户的流量 — 不是本流水线的负载」
- **按主机分组** - 多个模型共用一个网关时只探一次
- **标注归属** - 哪些模型是我们真调过的（高亮）
- **不暴露 vs. 0** - `/metrics` 拿不到时写「不暴露」，绝不回填 0

## 图标说明

### 步骤状态
- `▶` 正在运行（绿色）
- `⏸` 已暂停/停滞（黄色）
- `✓` 已完成（灰色，`--all` 展开）
- `⚠` 产出过期/缺失（黄色）
- `○` 未开始（灰色）

### 端点状态
- `✓` 正常（绿色）
- `✗` 离线/异常（红色）

### 速率趋势
- `↑` 加速中（绿色）
- `→` 平稳
- `↓` 减速中（黄色）

### 进度标记
- `+` 实际调用数超出预期（重试、JSON 重出会多打）

## 关键区别（panel.py vs. 旧版）

### 旧版 bug 1：端点负载混淆
- **旧版**：把端点整机的 `运行5 排队8` 直接印在模型名后面
- **真相**：那是**其他租户**的流量，本流水线一次没打过
- **新版**：明确标注「整机口径，含其他租户」，按主机分组，标出哪些是我们真用的

### 旧版 bug 2：过期步骤误报完成
- **旧版**：s04 产出被删掉，cache 目录还在，照样报「✓ 已完成」
- **真相**：产出不存在，这步本轮需重跑
- **新版**：比对输出 mtime vs. 输入 mtime，过期的标 `⚠` 并明确告知「本轮仍需重跑」

### 旧版 bug 3：数据口径不对
- **旧版**：进程 30 分钟前起的，改了 `RP_SEED` 但进程没重起，看不出在跑 453 还是 20
- **真相**：进程用旧版配置，正在跑全量 453 条（本该 20 条）
- **新版**：交叉验证 `RP_SEED`（声明）vs. `s01_filter.jsonl` 行数（实际），不一致时报警

## 技术细节

### 数据源（按可信度排列）
1. **cache/<stage>/*.json** - 含 `model` 字段，本流水线的调用归属，**唯一权威**
2. **cache/_events.jsonl** - start/end 配对，此刻在飞的请求、失败率
3. **data/*.jsonl** - 各步产出行数，数据口径交叉验证
4. **端点 /metrics** - 整机负载（含他人），拿不到就显式写「不暴露」

### 速率趋势判断
- 记录最近 6 个采样点（每 5s 一个）
- 比较前半段和后半段平均值
- 加速：后段 > 前段 × 1.15
- 减速：后段 < 前段 × 0.85

### 过期检测
- 比对输出文件 mtime vs. 输入文件 mtime
- 输出早于输入 → `⚠ 产出早于输入`
- 输出不存在但有 cache → `⚠ 产出不存在`

### 数据口径验证
- 声明：`RP_SEED` 环境变量或推定
- 实际：`s01_filter.jsonl` 行数（s01 每条输入一次调用，行数不会说谎）
- 不一致时：报警并用实际值算进度分母

## 常见问题

### Q: 为什么「本流水线的调用」和「端点」显示的数字不一样？
A: 「本流水线」是我们自己的流量，「端点」是整机负载（含其他租户）。旧版把两者混在一起，导致「用的模型显示 0，没用的显示忙」的反常现象。

### Q: 为什么 deepseek 显示「整机 运行5 排队8」但我们一次没用过？
A: 那是同一台机器上**其他租户**的流量。新版明确标注「整机口径，含其他租户的流量 — 不是本流水线的负载」，并在模型名那行标注「本流水线未调用」。

### Q: 为什么 s04 标 `⚠ 产出不存在` 但 cache 目录有文件？
A: 那是上一轮的残留 cache。本轮开跑前产出被删掉了，这步需要重跑（缓存可复用，但产出得重新生成）。

### Q: 为什么 s01 显示「实际 453 条」但声明是 20 条？
A: 进程可能起在改动之前，用的旧版配置。新版交叉验证 `RP_SEED`（声明）vs. `s01_filter.jsonl` 行数（实际），发现不一致就报警。

### Q: 为什么成功率不是 100%？
A: LLM 调用可能因为 JSON 格式错误、超时等原因失败，流水线会自动重试。成功率 >90% 是正常的。

### Q: 为什么 ETA 是 `-`？
A: 某些步骤无法预估总调用数（如未在 PIPE 中登记、或纯计算步骤如 s09），此时 ETA 无法计算。

### Q: 思维链占比很高正常吗？
A: GLM/DeepSeek 等模型的思维链 token 可能占输出 token 的 30-90%，这是正常的。

### Q: 进度显示 `2564/2238+` 是什么意思？
A: 实际调用 2564 次，预期 2238 次，超出的部分是重试或 JSON 重出。`+` 标记提示「实际超出预期」。
