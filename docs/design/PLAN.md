## 1. 当前唯一阻塞项：模型端点

流程有三处硬性要求多模型，没有端点无法往下：

| 步 | 要求 | 原因 |
|---|---|---|
| 6 Multi-Model Aggregation | **≥ 2 个异质模型**（不同厂商/系列） | 同系列共享盲区，取并集等于白跑 |
| 11 RIFT 诊断 | 异质组合，按失效模式选型 | Gemini 系强于 Ungrounded/Subjective，GPT 系强于 Missing/Low Signal |
| 12 判分 | **判分器 ≠ 生成器** | 自偏好偏差会让判分虚高 |

我需要你提供（或告诉我在开发机上怎么取）：

```
base_url    OpenAI 兼容的 /v1 地址（vLLM 起的服务即可）
model_id    模型名
api_key     没有鉴权填任意字符串
family      标个厂商/系列名，用于校验异质性
```

至少两个。本机 `ANTHROPIC_BASE_URL` 是 Claude Code 自己的凭据，
不建议拿来跑几万次批量调用。

配置写进 `config/models.json`，格式：

```json
[
  {"name": "gen-main",  "model_id": "...", "base_url": "http://...:8000/v1",
   "api_key": "x", "family": "qwen",  "roles": ["generator"]},
  {"name": "gen-alt",   "model_id": "...", "base_url": "http://...:8001/v1",
   "api_key": "x", "family": "intern", "roles": ["generator", "diagnoser"]},
  {"name": "judge",     "model_id": "...", "base_url": "http://...:8002/v1",
   "api_key": "x", "family": "glm",   "roles": ["judge"]}
]
```

启动时会校验：generator 与 judge 的 `family` 不同、generator 至少两个 family。

## 2. 分阶段计划

每阶段结束都有一个「不达标就别往下」的检查点。调用量是**估算**，
含缓存命中后重跑不再计费。

### Phase 1：20 条试跑（约 400 次调用）

单模型，忠实实现 RET。目的是调 prompt 和 schema，不看指标。

- 跑步骤 1 → 9，跳过 6（多模型）、10（回复池）、11 的需池两项
- 抽样规则：open/closed 按 7:3，含 1 条超短 query、1 条多子题、1 条非中文

**检查点**：
1. 维度去重数从 1 涨到 ≥ 4 —— **这条不过，后面全部无意义**
2. 题型判定人工核对 20 条，错 ≤ 2 条
3. 所有输出 JSON 可解析（schema 稳定性）
4. `multi_part` 在那道多子题上真的分了 block，没压平成并列准则

这一步是**单位 token 信息量最高的**。RET 若在我们这种散学科分布上导不出多样视角，
整个骨架选择就得重议，而这只花 400 次调用就能知道。

### Phase 2：453 条结构跑（约 9k–12k 次调用）

单模型全量。产出可以给人看的东西。

- 跑 1 → 9 + 步骤 11 的五项免池诊断
- 填出 xlsx 的 A/B/C 三列，另存新文件（不覆盖原表）

**检查点**（对照 `baseline.json`）：

| 指标 | 基线 | 目标 |
|---|---|---|
| 维度去重数 | 1 | ≥ 4 |
| 知识正确性占比 | 100% | ≤ 50% |
| 每题满分 | 10–61 | 恒 1.0（归一后） |
| 模板化负向项占比 | 98% | ≤ 10% |
| 题内准则最大相似度 | 未控 | < 0.7 |
| 改写率（A 列判「是」+「弃用」） | — | 4%–8%，显著超出说明保守约束没生效 |

### Phase 3：加多模型聚合 + RIFT 免池诊断（约 +10k–14k）

- 第二个模型独立跑 2 → 5，聚合出 R_base
- 五项免池诊断上 LLMaJ-MV（N=5），但 Redundant / Low Signal 用单次跑

**检查点**：
1. 聚合后维度数 > 单模型（不涨就说明两个模型不够异质，换模型）
2. RIFT 五项各自的触发率。**Redundant 触发率若显著偏高**，
   说明去掉「背景知识假设」确实需要补回来（这是那个决定的验证点）

### Phase 4：回复池 + 判分 + 端到端（约 +10k–15k）

这里有个必须先定的事：**锚定回复不能等于待评回复**。

- 389 条双回复的：glm52 作锚（步骤 5），gpt55 进评测池
- 64 条单回复的：**先排除**，不然锚和待评同源，rubric 会从待评回复自身衍生
- 弱档：生成 453 条（截断 / 删关键论点 / 小模型 三种各三分之一）

**检查点**：
1. Hackable / Low Signal 触发率
2. **端到端**：用新 rubric 和草稿 rubric 分别给「gpt55 vs 弱档」打分，
   比 pairwise 一致率。新 rubric 不超过草稿就不上线
3. major 闸门命中率落在 5%–20%（>30% 定太松，<3% 形同虚设）

判分是最大成本项（453 × 准则数 × 回复档数）。**可以只在 150 条子集上判**——
结构指标在这个量级已稳定，只有端到端对比需要更大样本。

### Phase 5：锚点集（人工）

- 抽 60 条 × 约 6 条准则 ≈ 360 个准则级标注
- 分层：三种 form 按实际占比，学科覆盖理/工/医/人文
- 额外审**题型判定**的正确性（v2 新增环节，没有历史数据）
- 重点审 RIFT 自动诊断最弱的两类：Misaligned or Rigid（PWA 80%）、Hackable
- **这批数据不进任何训练集**

## 3. 两个需要你拍板的设计选择

### 3.1 RET 忠实实现 vs 批量实现

| | 忠实 | 批量 |
|---|---|---|
| 做法 | 每个树操作一次 LLM 调用 | 一两次调用出整棵树 |
| 每题调用量 | ~16 | ~2 |
| 453 条成本 | 约 7k | 约 900 |
| 风险 | 贵 | **可能丢掉 R_w 的效力** |

R_w（「这层还漏了什么」）是我们选 Qworld 的**唯一理由**。批量实现时它退化成
prompt 里一句「请覆盖全面」，那就等于没选它。

**我的建议**：R_h 批量、R_w 忠实。即一次调用出场景和视角骨架，
然后单独调用问「还漏了什么视角」。折中后每题约 5–6 次调用，
且保住了载重部件。Phase 1 两种都跑 20 条，直接比维度数。

### 3.2 那 64 条单回复记录怎么处理

| 方案 | 代价 |
|---|---|
| A. 排除，只跑 389 条 | 样本少 14%，但最干净 |
| B. 集群上补生成一条参考回复 | +64 次生成，全量保留 |
| C. 保留但跳过步骤 5 锚定 | 这 64 条的 rubric 质量与其余不可比 |

**我的建议**：Phase 2/3（不判分，只看结构）用全部 453 条；
Phase 4（要判分）用 A 方案的 389 条。理由是结构指标不涉及锚定与待评的冲突，
而判分涉及。

## 4. 目录结构

```
~/rubric_pipeline/
  config/models.json        ← 待你填
  lib/{xlsx,llm,schema}.py
  prompts/s{02,025,03,04,05,06,07,08,11}.txt
  stages/s00_seed.py ... s14_report.py
  data/
    seed.jsonl              ← 已生成
    baseline.json           ← 已生成
    s02_context.jsonl       每步一个文件，可单独重跑
    ...
    rubrics_final.jsonl
    filled.xlsx             ← 最终交付
  cache/<stage>/<hash>.json ← 按 (模型,prompt) 哈希缓存
  reports/
```

每步独立读写 jsonl，任一步挂了可单独重跑。缓存按内容哈希，
调 prompt 只重算受影响的步。
